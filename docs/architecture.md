# ScopeDesk implementation

ScopeDesk is an independently runnable Flask/Jinja application. It uses Python services and a small DB-API adapter copied from LoopDesk for parameterised SQLite/psycopg queries. There is no runtime dependency on the LoopDesk checkout. LoopDesk vendors the same bounded JSON contract; a parity test checks the two copies when both checkouts are present.

`domain.py` parses CSV, interprets explicit mappings, validates structured edits, reconciles quantities, generates findings, groups exports and fills clarification templates. `services.py` scopes commands by workspace/case, preserves immutable sources and original rows, applies optimistic version checks, writes audit events and creates reviewed snapshots in transactions. HTTP handlers and tests use these services. A source correction is an overlay with a reason and resolvable references; the input row never changes.

Requirements, allocations, duplicate decisions, assumptions and follow-ups are stored as validated JSON in `cases.state`. Sources, individual source rows, clarification statements, reviewed revisions, import previews and audit events have relational records. This is a deliberately compact aggregate model rather than separate tables for each editable line. SQLite and PostgreSQL share the same forward-only migration files. Migration execution is explicit and never happens at import or build time.

The review snapshot contains the full case state, original sources, interpreted rows and findings at that point. A reviewed handoff contains only grouped scope, assumptions, follow-ups and reference labels/origins. It excludes the raw enquiry/CSV and serial-number values. The frozen payload is canonical JSON with a SHA-256 digest computed without the digest field. The digest checks integrity, not customer authenticity. Any later change increments the case version; previous revisions are shown as superseded and cannot generate a fresh CRM handoff.

Equipment counts and media counts are independent. Equipment allocations must conserve each included row. Reuse and whole-item destruction may be allocated to disjoint quantities; their combined allocation cannot exceed the parent count. Embedded-media actions can coexist with equipment reuse. Media action counts are entered independently and compared against confirmed embedded-media requirements where supplied. Loose-media actions conserve their own parent rows. Overall and per-site requirements are checked separately. Exact mismatches block; approximate differences need acknowledgement and a count basis, which is exported as an assumption. On-site data restrictions are distinct from subsequent equipment collection.

Mapping previews are workspace-scoped, persisted and bound to the exact mapping/version. Server-side confirmation refuses a mapping that was not previewed. Missing/malformed quantities stay unknown; a blank CSV record is retained. Source references use logical record numbers, not physical line numbers, so quoted multiline cells remain unambiguous. Every confirmed detail must resolve to an immutable source line or CSV cell. Reviewers remain responsible for verifying the semantic support of a citation; deterministic validation does not understand free-text enquiry meaning.

LoopDesk migration `002_scopedesk.sql` adds workspace-scoped case links, immutable received revisions and upload previews. Confirmation validates active CRM relationships, inserts the opportunity/link/import/history atomically, and checks latest revision and canonical payload on every attempt. Newer scopes preserve existing CRM fields; their suggested next action appears in activity history. Repeating the latest identical revision returns the same opportunity; any revision older than the latest received is rejected. Composite foreign keys scope linked opportunity records to their workspace. PostgreSQL uses a row lock for existing case links; uniqueness constraints arbitrate simultaneous first imports.

The UI uses escaped Jinja and safe DOM text creation, labelled native controls, visible focus, keyboard-scrollable tables and responsive layouts. No customer messages are sent. The no-JavaScript fallback exposes the validated JSON editor; the normal UI provides individual structured fields. The worked-correction button only populates the form after the synthetic customer clarification has been recorded; the reviewer still saves and reviews explicitly.

`presentation.py` groups findings and labels compact source-row/line links without changing domain codes or exported data. Native details retain exact references. The existing per-finding reference cap and overflow notice remain in place to bound aggregate output; sources and allocation evidence are retained. The case summary uses the same `review_assumptions` helper as immutable revision creation. Optional examples in `demo.py` use ordinary case creation, CSV preview/mapping/commit and state-save services, including atomic workspace quotas. The example-loading POST accepts only three fixed keys and selects existing examples within the active workspace; there is no schema or handoff-contract change.

Limits: 32 KiB enquiry/statement, 256 KiB CSV, 1,000 CSV records, 20 columns, 4 KiB per CSV cell, 160 bytes per header, 240 KiB scope state, 48 KiB handoff. Integer quantities range from zero to 9,999,999; unknown is JSON null. Duplicate/empty headers, invalid UTF-8, malformed record widths and unsupported units produce explicit errors/findings. Draft exports identify unknown values and their draft status. Spreadsheet formula prefixes are neutralised in CSV.

Demo isolation is provided by a signed, HttpOnly, SameSite cookie and a server-side 24-hour expiry check on every protected route. ScopeDesk uses `scopedesk_session`; LoopDesk retains `session`. Both can run on 127.0.0.1 with separate state. CSRF protects POSTs, version predicates reject stale commands, transaction rollback includes audit history, and no request can select another workspace. Expired data is removed opportunistically during the next workspace creation. This is a synthetic portfolio demo, with no real-customer authentication, background cleanup guarantee, backups or production operations claim.
